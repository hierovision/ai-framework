# Plan: rm-005

## Goal / Approach

Give the library one machine-readable inventory of itself: a `registry.json`
naming every skill and persona with owner, maturity, status, and a
resolvable boundary reference — validator-enforced so it cannot drift from
the repo, and consumed by the eval tooling instead of their re-derivation.
This closes RM-005 ("Machine-readable manifest listing each skill/agent:
owner, maturity level, boundary ref. Consumed by tooling") and unblocks
RM-008 (encoded boundaries), RM-009 (ROI per owner), and RM-011 (drift per
skill), which all need exactly this join table.

Approach: (1) `registry.json` at repo root — one entry per skill dir
(`skills/*`) and persona file (`agents/*.md`); (2) a loader module
`scripts/registry.py` — the single source of truth for reading it, exposing
`load()` / `validate()`, following the existing single-source import
pattern (`query_runs.CORE_SKILLS` imported by `changed-files-to-skills.py`
and `validate_skill.py`); (3) `validate_skill.py --all` cross-checks repo
reality ↔ registry (orphans, ghosts, incomplete fields, unresolvable
boundary refs) so a stale registry fails the pre-commit gate; (4)
`query_runs.coverage_gaps` honors registry `status: deferred` — a declared
deferral is a state, not a `no_default_marker` gap; (5) the registry is
recorded as a decision (ADR-0009 per the three-tier memory rule) and wired
into the contribution rule ("a new skill must register").

Deliberately minimal field set, pinned by the ROADMAP AC: `name`, `type`
(`skill` | `persona`), `owner`, `maturity`, `status`, `boundary_ref`. Eval
canary markers stay in `evals/evals.json` (their existing single source —
the registry references, never duplicates them). Model bindings stay OUT of
the registry (Layer-6 volatile facts live in `reference/model-routing.md`
and the `agents/*.md` `model:` lines; the registry is not a second place
for churn to land).

## Schema / Type Impacts

None (no DB, no generated types). The new data contract is the registry
entry shape, owned by `scripts/registry.py`:

```json
{
  "name": "observing-runs",
  "type": "skill",
  "owner": "@hierovision",
  "maturity": "L4",
  "status": "active",
  "boundary_ref": "skills/observing-runs/SKILL.md"
}
```

Rules: `type` ∈ {skill, persona}; `maturity` ∈ {L1, L2, L3, L4} (legend:
L1 provisional · L2 defined · L3 evaluated/operated · L4 capable —
consistent with `docs/maturity-plan.md` §3 usage); `status` ∈ {active,
deferred, deprecated}; `boundary_ref` must resolve (validator-checked).
Personas resolve `boundary_ref` to their `agents/<name>.md`. A deprecated
skill keeps its entry with `status: deprecated` (history, not deletion).
Do not hand-edit consumers' parsing — import the loader.
