# Plan: rm-002

## Goal / Approach

Goal: every skill change is gated by a behavioral (fresh-agent) eval run that
blocks regressions — no manual "I tried it" gates (Eval L1 -> L4, per
`docs/maturity-plan.md` §4/§5-B).

Approach: add a GitHub Actions workflow that runs the framework's existing
fresh-agent eval protocol headlessly via opencode, asserts each
`evals/evals.json` `expected_behavior` against the fresh agent's output, fails
the build on any regression, and emits a run-log record per eval via RM-001's
`log_run.py`. A hermetic offline unit test of the runner's assertion logic
(stub agent, no model) proves the gate fails-when-wrong and passes-when-right
without needing a model in CI's offline gate. Evals flagged `deferred: true`
are skipped by default. The existing offline `ci.yml` gate is intentionally NOT
modified — behavioral evals run in this new separate workflow.

**Free-tier cadence constraint:** GitHub Free private repos include **2,000
GitHub-hosted runner minutes/month** (source: GitHub Actions billing + Usage
limits). A *nightly* full run of ~63 evals (≈2–5 min/eval → ~126–315 min/run)
would consume ~3,800–9,500 min/month and exceed the cap. Default schedule is
therefore **weekly cron (`0 6 * * 1`) + `workflow_dispatch`** (weekly ≈ 540–
1,355 min/month, within budget). The cheap per-PR gate stays in `ci.yml`
(offline structural verifiers); the expensive live-agent eval runs on the weekly
schedule. See "Free-tier adherence" below.

### Free-tier adherence (GitHub Free, private repo — verified against official docs)

Every workflow claim in this plan is grounded in GitHub's documentation for
Free private repositories; no assumption:

- **Runner minutes:** 2,000 min/month on GitHub-hosted runners (Linux). Usage
  beyond quota is billed, or **blocked** if no payment method is on file
  (source: `docs.github.com/en/billing/managing-billing-for-your-products/
  managing-billing-for-github-actions` — Free row: 2,000 min). → schedule is
  weekly, not nightly; the runner supports `--limit` / subset sharding to stay
  in budget.
- **Triggers:** `on.schedule` (cron) and `workflow_dispatch` are available on
  Free (GitHub Actions is available on all GitHub products; triggers are not
  plan-gated) (source: `events-that-trigger-workflows`; usage-limits
  "Availability").
- **Artifact storage:** 500 MB included (shared with Packages) — run logs are
  KB-scale, well within (source: usage-limits storage table).
- **Artifact retention:** `retention-days` cannot exceed the limit set by the
  repo/org/enterprise; private-repo default is **90 days**, so `retention-days: 30`
  is safely within (source: `managing-github-actions-settings-for-a-repository`
  — "Configuring the retention period for GitHub Actions artifacts and logs in
  your repository" states the 90-day default; `storing-workflow-data-as-artifacts`
  confirms the `retention-days` cannot-exceed rule).
- **Secrets:** repository-level secrets ARE available on Free; **organization-
  level secrets are NOT accessible by private repos on GitHub Free** → the
  model-access credential MUST be a **repository secret**, not org-level
  (source: `security-guides/encrypted-secrets` — "Organization-level secrets
  ... are not accessible by private repositories for GitHub Free").
- **Permissions / concurrency:** `permissions: contents: read` and
  `concurrency` are supported on Free (existing `ci.yml` already uses them;
  Free allows 20 concurrent jobs).
- **Model cost is external to GitHub:** the `secrets.*` value is an API key for
  the model/opencode provider, billed by that provider — NOT part of GitHub
  Actions minutes. Free-tier adherence here concerns only runner minutes.

## Model-cost policy (CI) — free-tier-only, no paid usage

**Hard constraint (user, 2026-08-28):** *Zen-tier actual cost must be avoided;
only free-tier ("free tier zen") models may be used in CI.*

On this library's routing (`reference/model-routing.md`, "Provider notes" +
"Free-tier fallback"), the **Free tier** is the `opencode/*-free` catalog IDs —
explicitly "a subset of the Zen catalog" billed at **$0**. So "free tier zen
models" = the `*-free` IDs. The permitted CI model set is therefore **`*-free`
only**, which inherently excludes both **Zen PAYG** (proprietary, paid) and
**Go flat-rate** ($10/mo, paid).

Enforcement mechanism (already exists): set **`AI_FRAMEWORK_FREE_TIER=1`** in
the workflow — `reference/model-routing.md` states this "forces the free tier
even when a Go/Zen key is present."

Consequences:
- The model-access secret (`OPENCODE_API_KEY`) is still required for
  **authentication** to the opencode API, but with `AI_FRAMEWORK_FREE_TIER=1`
  only `*-free` IDs are ever selected, so usage stays $0 (no Zen PAYG, no Go).
- Any eval whose coverage requires a Go or Zen (paid) model to be meaningful
  MUST be marked `deferred: true` and is excluded from the scheduled run; it can
  be run on-demand by a developer locally, where paid tiers are allowed.
- The authoring-skills eval protocol's "test on one Go-tier + one Zen-tier model"
  rule (`skills/authoring-skills/SKILL.md`) applies to *developer* authoring,
  not to the CI run. CI coverage is free-only by policy.

## Scope

Included:
- Scheduled + manual-dispatch workflow running behavioral evals.
- Headless runner that consumes existing `evals/evals.json` and asserts
  `expected_behavior`.
- Offline unit test of runner logic (stub agent) — the gate is verifiable
  without a model.
- Per-eval run-log emission via RM-001 helper.
- Deferral handling for real-browser/harness-unavailable evals.

Excluded:
- Editing the existing offline `ci.yml` gate (behavioral evals live in the new
  separate workflow).
- Nightly full-eval runs (exceed GitHub Free's 2,000 min/month — default is
  weekly; see Free-tier adherence).
- Organization-level secrets for model access (unavailable to private Free
  repos — must use a repository-level secret).
- Any Go flat-rate ($10/mo) or Zen PAYG (proprietary, paid) model usage in CI —
  CI is restricted to `*-free` (the $0 tier) only (see Model-cost policy). Paid-
  tier evals must be marked `deferred: true` and run only on-demand by a
  developer, never in the scheduled job.
- Provisioning the model-access secret / CI credential setup (precondition;
  reference `securing-ci` — workflow consumes it without echoing, does not
  create it).
- Drift scoring / historical trend dashboards (RM-003, RM-011).
- Rewriting existing evals; only consuming them.

## Schema / Type Impacts

Consumes RM-001's JSONL run-log schema (no new schema here). The runner writes
eval-kind records via `log_run.py` with `kind="eval"`, `skill=<skill>`,
`eval_pass=bool`, `outcome=success|failure`. No DB, no generated types. The
`evals/evals.json` format gains OPTIONAL per-eval `deferred: true` and OPTIONAL
per-eval / top-level `default_model_tier` with allowed values `free | go | zen` —
additive, backward-compatible. An eval with no `default_model_tier` defaults to
`free` (so it runs under `AI_FRAMEWORK_FREE_TIER=1`); `go`/`zen` evals are skipped
in CI mode and must be `deferred` for developer-local paid runs. This is a
contract extension to the eval protocol owned by `authoring-skills`; document in
its SKILL.md.
