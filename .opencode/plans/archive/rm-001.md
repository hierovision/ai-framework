# Plan: rm-001

## Goal / Approach

Goal: make every skill/agent/eval execution observable through a structured,
queryable run log so the framework can answer "why did the agent do X, and did
it regress?" (Observability L1 -> L4, per `docs/maturity-plan.md` §4/§5-A).

Approach: introduce a new `observing-runs` skill that owns (a) the canonical
JSONL run-log schema — the single source of truth, (b) a `log_run.py` helper
that appends one line per execution, and (c) a `query_runs.py` aggregator
(cost/task, latency, eval-pass rate, raw drift signal). Run logs default to `logs/run-<date>.jsonl` (one file per UTC day), git-
ignored, file-based only (maturity plan §8: zero external services). Daily
rotation plus `query_runs.py prune --older-than 30d` (default 30-day retention,
delete-or-gzip) bounds disk growth; CI artifacts carry their own 30-day
retention (RM-002). **ROI guardrail (deliberate):** logging is strictly out-of-context *at
runtime* — records are appended to a file on disk and are read ONLY out-of-band
(humans via `query_runs.py`, CI via RM-002/RM-003, ROI/drift scripts via
RM-009/RM-011), never injected into the agent's own live prompt for "self-
awareness"; emission is once per run, not per internal sub-step; the query
script is opt-in (run on demand), never per turn. Logs are NOT write-only —
they have a concrete read path (see Scope). This keeps logging cost bounded to
~~<1%~~ <2% of a run's tokens (revised 2026-09-06; the number is `unverified`
— see `reference/run-log-overhead.md`) (one `log_run.py` tool call ≈ 80–160 tokens vs
thousands per task) and eliminable entirely via hook-based emission (Open
Question 1). Full "automatic on every invocation" depends on opencode hook
support; v1 ships schema + helper + query + convention docs + a best-effort
`opencode.json` hooks snippet, with RM-002's eval runner as the first
consuming caller.

## Acceptance Criteria

1. **`log_run.py` appends one well-formed JSONL record with all schema fields**
   (ts, run_id, kind, skill, agent, model, tokens_in, tokens_out, duration_ms,
   outcome, eval_pass, detail) — verifier:
   `python3 skills/observing-runs/scripts/test_log.py` runs a red/green unit
   check — valid JSON parsed, all required keys present, exactly one line
   appended, exit 0; a call omitting a required field exits non-zero.

2. **`log_run.py` is symlink-install safe** (run-as-main gate uses
   `realpath` of `argv[1]`, matching the library's documented ESM/CLI gate
   rule) — verifier: `test_log.py` invokes the script both via its repo path
   and via a symlink under a temp `~/.config/opencode/skills/observing-runs`
   and asserts a record is still written in both cases.

3. **`query_runs.py` returns deterministic aggregates over seeded
   `run-*.jsonl` fixtures** — per-skill token totals (cost/task), mean
   `duration_ms` (latency), eval-pass rate (`eval_pass==true` / eval-kind
   rows) — verifier: `python3 skills/observing-runs/scripts/test_query.py`
   exits 0 with computed values equal to the expected numbers embedded in the
   fixture.

4. **The `observing-runs` SKILL.md documents the schema as the single source
   of truth plus the logging convention and a hooks snippet reference** —
   verifier: `python3 skills/authoring-skills/scripts/validate_skill.py --all`
   exits 0 for the new skill AND `grep -n "schema.md\|hooks.opencode.json"
   skills/observing-runs/SKILL.md` matches both links.

5. **`logs/` is git-ignored so telemetry is never committed** — verifier:
   `git check-ignore logs/run-2026-01-01.jsonl` exits 0 (path ignored).

6. **Logging is out-of-context, append-only, non-blocking, and per-run**
   (the ROI guardrail): `log_run.py` returns immediately after a single file
   append and reads no prior log content; the `observing-runs` SKILL.md
   forbids feeding logs back into agent context and per-sub-step logging;
   emission granularity is one record per run, not per tool call — verifier:
   `grep -nE "for.*in.*read|context.*log|self-?aware" skills/observing-runs/
   SKILL.md references/schema.md` finds NO instruction to read logs into
   context, AND `test_log.py` asserts `log_run.py` performs one append and
   exits 0 without reading the log file back, AND `grep -nE "RM-002|RM-003|
  RM-009|RM-011|query_runs" skills/observing-runs/SKILL.md` matches the
  documented out-of-band consumers (proving logs are read, not write-only).

7. **Retention is bounded and prunable** — `query_runs.py prune --older-than N`
   removes daily files older than N days (or gzips them with `--archive`) and
   keeps newer ones; `--dry-run` removes nothing — verifier:
   `python3 skills/observing-runs/scripts/test_prune.py` seeds files with
   faked mtimes (old + new), asserts prune deletes only the older set and exits
   0, and asserts `--dry-run` deletes nothing.

## Scope

Included:
- Canonical JSONL run-log schema + reference doc.
- `log_run.py` helper (emit one record) + `query_runs.py` aggregator.
- `observing-runs` skill documenting the convention + hooks snippet.
- Unit tests proving emission/aggregation fail-when-wrong and pass-when-right.
- Git-ignore for `logs/`.
- Documented read path (logs are NOT write-only): consumed by humans
  (`query_runs.py`), CI (RM-002 eval gate + RM-003 report artifact), and
  RM-009 (ROI 4 numbers) / RM-011 (drift) scripts — all out-of-band, on
  schedule or on demand.

Excluded:
- Auto-instrumenting all 21 existing skills/agents to call `log_run.py`
  (adoption is incremental; RM-002 is the first consumer).
- Live token/duration capture from opencode internals (depends on hook
  availability — see Open Questions).
- **Feeding run-log content back into the agent's context window** (anti-
  pattern; defeats the ROI guardrail) — explicitly forbidden.
- **Per-internal-sub-step logging** (e.g. one record per tool call) — emission
  is once per run only; sub-step tracing is out of scope for v1.
- Drift scoring beyond a raw per-skill eval-pass-rate trend (RM-011 owns
  drift detection).
- Any external telemetry service / database (file-based only, per maturity
  plan §8).
- **Raw prompt / output / tool-call transcript capture** (noise + privacy +
  cost) — `detail` is failure-only and capped at 512 chars; full I/O is never
  logged.
- **Permanent / infinite retention** — logs are pruned (see Retention);
  only rolled-up aggregates persist. Growth is bounded by design.

## Schema / Type Impacts

New shared schema (file-based, no DB): `skills/observing-runs/references/
schema.md` defines the JSONL contract. Fields:
- `ts` (string, ISO-8601 UTC)
- `run_id` (string, uuid)
- `kind` (enum: `skill` | `agent` | `eval`)
- `skill` (string | null)
- `agent` (string | null)
- `model` (string | null)
- `tokens_in` (int | null, ~~default 0~~ superseded 2026-09-06 → null when unknown)
- `tokens_out` (int | null, ~~default 0~~ superseded 2026-09-06 → null when unknown)
- `duration_ms` (int | null, ~~default 0~~ superseded 2026-09-06 → null when unknown)
- `outcome` (enum: `success` | `failure` | `error` | `stopped`)
- `eval_pass` (bool | null)
- `detail` (string, optional)

No database, no generated types. This schema file is the single source of
truth; RM-002's eval runner MUST import `log_run.py` and must not redefine
field names.

### What gets logged (events + signal discipline)

Two event sources generate records in v1 — deliberately narrow, so the log is
high-value and low-noise, not a growing transcript dump:

- **Eval runs (RM-002):** one record per eval prompt — `kind=eval`,
  `skill=<skill>`, `model=<tier used>`, `tokens_in/out` (if exposed),
  `duration_ms`, `outcome`, `eval_pass`. Volume is bounded: ~63 evals/night
  across 21 skills (one record each) — a few hundred lines/day at most.
- **Skill/agent invocations (convention-based, adoption-gated):** one record
  per run (`kind=skill` | `agent`) with the same core fields. NOT auto-wired
  into all 21 skills in v1 (see Excluded).

Per-field value (why it is highest-value, not noise):
- `tokens_in/out` -> cost / ROI (RM-009). Highest.
- `duration_ms` -> speed / latency (target axis). Highest.
- `outcome` + `eval_pass` -> regression / quality (target axis). Highest.
- `skill` / `agent` / `model` -> attribution / slice. Highest.
- `ts` / `run_id` -> correlation metadata only.
- `detail` -> OPTIONAL, FAILURE-ONLY, capped at 512 chars; a short
  error/reason string. Never raw prompt or output.

Explicitly NOT logged (noise / privacy / cost): full prompts, full agent
outputs, intermediate tool-call transcripts, environment dumps, PII.

### Questions this data answers (future analytical surface)

The collected fields support, via `query_runs.py` / the RM-003 report / RM-009 /
RM-011, questions like:

- **Token efficiency:** token cost per successful task (tokens / outcome=
  success), per skill and per model; cost per eval-passing vs failing task;
  throughput (tokens per second). Feeds empirical model-routing re-optimization
  (`reference/model-routing.md`) instead of catalog-guess evidence.
- **Speed:** mean/median/p95 duration per skill; duration trend (are skills
  slowing as they grow?); duration-vs-model tradeoff.
- **Quality / reliability:** eval-pass rate per skill over time; outcome
  distribution (success/failure/error/stopped) per agent; failure-rate
  regression = the RM-011 drift score (eval-pass-rate slope).
- **Attribution / adoption:** which skills/agents are actually used (maintain
  vs retire); which model is bound to which agent and how it performs —
  validates the routing table empirically.
- **ROI (RM-009 — the 4 numbers):** duration -> hours x rate; failure-rate
  delta before/after a change; cycle-time delta; ramp-time avoided per project.
- **Root-cause ("why did the agent do X?"):** given ts + skill + model +
  detail, reconstruct a specific run's outcome (maturity plan §4 target
  question); `detail` carries the failure reason.
- **Coverage:** which skills have eval records (eval coverage) vs gaps.

Honest limits (by design): per-run granularity only — cannot attribute cost to
a single internal tool call; no raw I/O — cannot content-debug a transcript.
Both excluded deliberately for ROI/noise (see Excluded).

### Retention

- **Local:** `logs/run-<YYYY-MM-DD>.jsonl` is one file per UTC day.
  `query_runs.py prune --older-than 30d` deletes (or `--archive` gzips to
  `logs/archive/`) daily files older than the window. Default window 30 days
  (override `--older-than` / `OBSERVE_RETENTION_DAYS`); confirm window (OQ6).
- **CI (RM-002):** run logs uploaded as a workflow artifact with explicit
  30-day retention; artifacts auto-expire, so CI is never the long-term store.
- **Aggregates persist, raw lines don't:** RM-009 (ROI) / RM-011 (drift)
  derive rolled-up numbers from logs; once a daily file is pruned, the summary
  survives in the report, not the source lines.

## Open Questions

- OQ1 (logging mechanism / hook availability — also the token-ROI lever):
  opencode currently has no wired `hooks` in this repo. Full "emitted on every
  skill/agent invocation" requires an opencode hook event (per-agent/per-skill
  start-stop). **Proposed default: prefer hook-based emission** because a hook
  fires outside the agent's generation and costs the agent ZERO tokens, whereas
  convention-based logging (the agent calls `log_run.py`) adds ~1 tool call
  (~80–160 tokens) per run — bounded but non-zero. Ship `log_run.py` + a
  documented convention + a best-effort `opencode.json` hooks snippet, and
  verify the hook event model against current opencode docs
  (`validating-against-official-docs`) before claiming auto-instrumentation. If
  hooks are unavailable, v1 stays convention-based and full automation is
  deferred; the per-run (not per-sub-step) granularity keeps even the fallback
  cheap.
- OQ5 (overhead budget): convention-based logging should be measured once in
  CI (RM-002's first run) — if the per-run `log_run.py` tool-call overhead
  materially skews a skill's eval token totals, mandate hook-based emission
  before broad adoption. Proposed default: no hard threshold yet; review after
  the RM-002 baseline.
- OQ2 (token/duration capture): opencode may not expose per-invocation token
  counts to a hook/helper. Proposed default: `log_run.py` accepts
  `tokens_in/out` and `duration_ms` as caller-supplied args (the caller
  measures what it can); ~~fields default to 0 when unknown, never fabricated~~
  (superseded 2026-09-06 → null when unknown, never fabricated).
- OQ3 (stack reference): no `vue-supabase` (or any) stack reference matches
  this skills/agents Python+Node library; planning proceeded generically.
  Flagging the gap as a finding (consider adding a `skills-library` stack
  reference later).
- OQ4 (log location/rotation): default `logs/run-<date>.jsonl` (one file per
  UTC day) at repo root, git-ignored; CI may override via `OBSERVE_LOG_DIR`.
- OQ6 (retention window + disposition): proposed default **30 days** local
  prune window and **30-day** CI artifact retention; default disposition is
  DELETE, with opt-in `--archive` gzip to `logs/archive/`. Confirm the window
  (30 vs 90 days) and whether gzipped archive is preferred over delete before
  merge.
