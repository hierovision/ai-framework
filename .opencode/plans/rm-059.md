# Plan: rm-059

## Goal / Approach

`scripts/watch_agent.py` must stop reporting `STALLED` for a subagent whose
session stream is demonstrably advancing, while still firing `STALLED` on
genuine silence (RM-059, Now, score 6).

Root cause (probed live 2026-10-24, read-only): the verdict's session-stream
age measures part **creation** only — `analyze_session` takes the newest
`part.time_created`. ~~During a long generation opencode inserts no new part
rows but grows the current `reasoning`/`text` rows **in place**: the probe
showed a mid-generation `reasoning` part with `created_age=47s /
updated_age=2s` (the DB has a `time_updated` column `load_parts` ignores;
quiet sessions show equal ages, so the signal is real and discriminating).~~
~~(superseded 2026-10-25 — the live drill falsified in-place growth; see the
Revised block below.)~~ The child's heartbeat also stalls mid-generation (it
logs between calls), so `min(hb_age, s_age)` crosses the stall window and a
working child reads STALLED. RM-022's no-tool-durations fact stands — the
probe found tool parts still written once at completion (`start≈end`); this
fix does not touch that.

Approach (shipped 2026-10-25, stands): fix the stream-activity age at the
source. `load_parts` also selects `part.time_updated` and injects it into the
parsed part dict as `_time_updated` — **no tuple-arity change**, so the
`(ms, d)` unpacking in `has_terminal_result`, `session_guard._permission_denial`,
and `observe_completion` is untouched. `analyze_session` computes
`last_change_ms` (freshest of creation and in-place change, degrading to the
creation age when the key is absent). `verdict()` uses it as the stream age —
gating **both** `STALLED` and `DEAD` (one liveness variable; fixing only
STALLED would leave the false positive live at the DEAD tier). The STALLED
`why` line names its evidence basis (`no stream change for <age>`) per the
detail file's quiet-vs-delta convention.

### Revised 2026-10-25 — server-status lane + step-aware grace

The shipped in-place-delta premise is falsified: three live drill dispatches
(read-only `planner` children, full visibility flags, per-second polling —
`.scratch/rm-059-implement/live-drill/poll*.log`) showed **every DB delta was
a new-part insertion (8/8)**, the `--stream-out` tee is block-granular too
(a 2500-word essay arrived as ONE event), and the freshest DB clock went
quiet mid-generation for up to ~86 s. The vendor publishes nothing on any
durable surface until a block boundary — so no DB/tee-based delta gate can
close a >240 s single-step generation.

Revised approach — two lanes in `verdict()`:

- **Lane A — server-aware, preferred.** When a known-port server URL
  resolves (`OPENCODE_WAKE_URL` env or a new `--server-url` flag — the
  framework's existing wake convention), the verdict polls `GET
  /session/status` for the child (vendor docs: "use the opencode server to
  interact programmatically"): `busy` = demonstrably advancing → never
  STALLED/DEAD; `retry` = surfaced in the why; `idle`/absent + the shared
  completion predicate = done. Community grounding: herdr #351 (trust
  `session.status` only — never map `session.updated`), #35472 (busy is
  trustworthy mid-run; idle transitions can lag), #30043 (parentID
  distinguishes child idle events).
- **Lane B — DB fallback (no server).** The shipped block-granular clock
  stands, plus step-aware grace: when the stream's newest part is an OPEN
  step (a trailing `step-start` with no `step-finish` after it — the same
  concept `observe_completion._assistant_step_closed` already encodes, kept
  one-semantics across surfaces like `has_terminal_result`), silence inside
  it stretches to `--generation-seconds` (proposed default 600 s, matching
  the ~10-minute dispatch bound) before STALLED may fire; beyond it STALLED
  then DEAD as usual. A quiet stretch NOT inside an open step (inter-block,
  post-turn) keeps the 240 s window.

### Revised 2026-10-25 — settled and new

1. **Which timestamp says "the child just wrote something"?**
   ~~Recommended: the last-changed timestamp on each entry of the child's
   session log...~~ **SETTLED — none. The live drill falsified the premise:
   no timestamp in `opencode.db` moves during token streaming (8/8 delta
   sightings were insertions); the tee is block-granular too. The liveness
   basis is the vendor's own status surface when a server URL resolves
   (Lane A), and step-aware grace otherwise (Lane B).**
2. **Fix the age once, or the false alarm survives under another name?**
   Recommended: fix once. STALLED and DEAD read the same age; correcting
   the age heals both. Correcting only STALLED leaves the false alarm
   escalating — DEAD authorizes the stronger intervention. (Holds for both
   lanes.)
3. **No playbook exists for this kind of repo.**
   Recommended: proceed anyway. The design skill ships playbook templates
   for web-app stacks (Vue or Next.js + Supabase). This repo is different
   — a library of Python scripts and agent skills — so no template
   applies and the plan reasons from first principles. No decision needed
   from you.
4. **How long may a generating step stay silent before it reads as a
   stall?** Recommended: `--generation-seconds` default 600 s — matches
   the ~10-minute dispatch checkpoint bound; outside an open step the
   plain 240 s window holds. Veto at approval.
5. **How should the vendor `retry` status surface?** Recommended: in the
   `why` only (retry state named), exit code stays 2 — no new verdict
