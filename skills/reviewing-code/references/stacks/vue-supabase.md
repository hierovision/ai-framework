`vue-supabase` (Vue 3 + TypeScript + Pinia + Vuetify 3, Supabase Postgres

## Row-Level Security on schema/policy diffs

RLS is the security backbone of this stack and the most consequential
thing a diff can get subtly wrong. When the diff touches `db/schema.sql`
or any policy:

- **Flag widening visibility.** A SELECT/UPDATE/DELETE policy that uses
  `USING (true)`, `USING (auth.uid() IS NOT NULL)`, or omits the
  `auth.uid() = <row>.user_id` scoping grants all authenticated users
  access to every row — a cross-user data leak. This is a blocker on a
  SELECT policy (read leak) and at least a major on a write policy.
  Compare the policy predicate to the plan's `Schema / Type Impacts`
  intent: a per-user row should scope to `auth.uid() = user_id` (or the
  sharing model the plan describes, e.g.
  `owner_id = auth.uid() OR sharee_id = auth.uid()`).
- **Flag a policy added without RLS enabled.**
  `alter table ... enable row level security;` must precede or accompany
  the policy; a policy on a table with RLS disabled is a no-op (every
  query bypasses it). Major unless the plan explicitly defers RLS.
- **Flag service-role bypass in client code.** Use of the
  `service_role` key in application code (`src/`) is a scope/security
  finding — service role bypasses RLS by design and belongs only in
  trusted migrations. Route to `implementing-features` to remove it
  unless the plan explicitly authorizes a migration-only use.
- **Check the policy shape matches existing tables.** Inconsistency
  (a new table using `auth.role() = 'authenticated'` while every
  existing table uses `auth.uid() = user_id`) is a minor unless it
  widens visibility, then it is the leak above.
- **Per the plan's contract.** If the plan's `Schema / Type Impacts`
  says `None.` and the diff edits `db/schema.sql`, that is a scope
  breach (see the SKILL.md scope-conformance check) — the schema touch
  is out of scope independent of whether the policy is correct.

## Generated DB types (never hand-edited)

`types/database.types.ts` (path per rules file) is a **build artifact**
regenerated by `npm run db:types`. On review:

- **Flag a hand-edit of the generated types file.** A diff hunk in
  `types/database.types.ts` that is not a full regeneration (a one-line
  field addition, a narrowed type, a cast inserted) introduces drift
  between schema and types that the next regen surfaces as a failing
  `git diff`. The correct edit is `npm run db:types` (or the rules-file
  regen command) committed wholesale; a hand-edit is a major (it masks
  schema/types drift). If the plan's `Schema / Type Impacts` said
  `None.`, a hand-edit of the generated types is also a scope breach.
- **Flag a code change that works around a missing generated type** with
  `as any` or `// @ts-ignore` — that is a suppressed contract break
  (the implement-time reference calls it out). Major; route to
  `implementing-features` to regen the types instead of suppressing.
- **A regenerated types diff is expected when the plan touches the
  schema** — it is in-scope only if `files/database.types.ts` (or the
  types path) is in the plan's Files to Modify and `Schema / Type
  Impacts` is non-`None.`. Otherwise it is scope creep.

## Vuetify semantic variables vs raw CSS

When the diff adds styling to a Vue component:

- **Flag raw CSS values that break on theme switch.** Hardcoded hex
  colors (`color: #1867c0`), raw `padding: 13px`, or inline styles defeat
  Vuetify's theming: they do not respond to dark mode or brand overrides.
  Prefer Vuetify's semantic CSS variables (`var(--v-theme-primary)`,
  `var(--v-theme-surface)`) and the theme spacing scale. This is a minor
  (maintainability) unless the AC names theme/contrast behaviour, then
  it can be major.
- **Flag hand-rolled native elements styled to match Vuetify** when a
  Vuetify component (`v-btn`, `v-card`, `v-dialog`) exists — hand-rolled
  markup loses the design system's accessibility and theming. Minor.
- **Flag an unregistered icon** — Vuetify's icon set is opt-in per icon,
  and an unregistered icon renders silently blank instead of erroring:
  a hard-to-spot regression. Minor (or major if an AC asserts the icon
  is visible).
- Out-of-scope cosmetic polish is not a review finding against the diff
  *content* unless it widened scope — the absence of polish is the
  plan's call, not the reviewer's.

## Pinia store + composable pattern conformance

When the diff adds a store or composable:

- **Flag a style break with the existing stores.** If the project uses
  Options-API stores (`defineStore('name', { state, actions })`), a
  new setup-syntax store (`defineStore('name', () => {...})`) is a
  mixed-codebase finding — minor (it will be flagged again at the next
  review and is out of scope to refactor mid-pass). The reverse applies
  symmetrically.
- **Flag state/getter/action shape divergence** from neighbouring
  stores — a new store that names actions inconsistently (`load()` vs
  the project's `fetch()` convention) is a minor.
- **Flag a component calling `supabase.from(...)` directly** when the
  plan routes that mutation through a store / the offline outbox — that
  bypass the implement-time reference calls out is a major (it breaks
  the offline/RLS-scoped path the plan names).
- **Flag a composable introduced without the plan naming it** — a
  `useSomething` that appeared from nowhere is scope creep (record it
  as a follow-up, do not flag the code itself as a bug; the minor is
  the unrecorded urge).

## E2E selector / timeout discipline in changed specs

When the diff touches a Playwright spec (`e2e/*.spec.ts`):

- **Flag `waitForTimeout(<ms>)`** in a changed spec — it sleeps rather
  than waits on a condition, masking flakiness and inflating run time.
  Treat it as a major (a latent flake the next slow CI will surface);
  the fix is `expect(...).toBeVisible()` / `waitForSelector` on a
  condition. Out-of-scope pre-existing instances are a follow-up, not a
  drive-by fix — but a *new* `waitForTimeout` in the diff is a finding.
- **Flag bare CSS selectors** tied to class names
  (`page.locator('.v-btn__content')`) when a role/accessible selector
  exists (`getByRole`, `getByLabelText`) — they break on the next
  Vuetify version and double as a missed accessibility check. Minor;
  major if an AC asserts accessibility.
- **Flag a test that mocks away the behaviour under test** — the e2e
  trio's discipline: a Playwright test that stubs the page's real
  journey has vacated its assertion (the cardinal rule's
  "mock-away-the-behaviour" form). Blocker.
- **Flag a meaningful test that can never go red** — a test that asserts
  a tautology (`expect(true).toBe(true)`, or an assertion vacated with
  `void x`). Blocker; cite the test trio's meaningfulness check.

## TypeScript hygiene

- **Flag `as any`** in the diff — a suppressed type gap. Major if it
  hides a real contract break (e.g. around generated types); route to
  `implementing-features` to narrow the type or regen.
- **Flag `// @ts-ignore` / `// eslint-disable-*`** added to get
  verification green — a suppressed failure is a deferred contract break.
  Major.
- **Flag `||` where `??` is intended** — `||` coerces `0` / `''` /
  `false` which is rarely intended; minor.
- These are maintainer/contract findings unless an AC asserts the typed
  behaviour, then they can be major.

## Where this stack trips a review

- **An RLS policy that "passes" but widens visibility.** `USING (true)`
  reads correctly to a tired reviewer; it leaks every row. The policy
  predicate must scope to the owning/sharing user — compare it to the
  plan's `Schema / Type Impacts` intent, not to "it compiles".
- **A hand-edit of `types/database.types.ts`** that looks like a tidy
  one-liner but drifts schema↔types on the next regen. Regenerate, do
  not hand-edit; the hand-edit is a major.
- **A new `waitForTimeout` in an e2e spec** that passes today and flakes
  on the next slow CI. Flag it on read, not after the flake.
- **A component calling `supabase.from(...)` directly** when the plan
  routes the mutation through the store/outbox. The bypass breaks the
  offline + RLS-scoped path; major.
- **`as any` masking a generated-types gap.** Suppressing the type
  error to green type-check hides the real fix (regen the types). Major.

Each of these is a contract or security break dressed up as a small
edit — the plan's `Files to Modify` + `Schema / Type Impacts` + the
policy predicate are the authority, not the diff's surface polish.
