## Observed

`reference/git-workflow.md` §Roadmap closure and `implementing-features` Step 10 already mandate same-PR status closure ("A PR that closes (or advances) a `docs/ROADMAP.md` item updates that row in the **same** PR: status → `done` (or `in-progress`), with the close date and the PR link in the row"). But `triaging-requirements` never defers to that rule; its own language ("Done items (shipped/closed since last pass) move to `Done`", "status moves are the only re-score trigger") reads as though triage owns status transitions. A consumer reading only the triage skill can reasonably conclude status follows triage passes.

Consumer consequence — `Stonegate-Software/paragon-learning-network` drifted into a triage-pass-gated lifecycle; two items sat Done-in-fact but Open-on-paper between passes (`feat-plan-record-schema`, shipped PR #36; `deploy-stages-and-iac`, W1–W7 complete). Owner directive 2026-10-12: "the session that implemented the feature must update the roadmap and plan and anything else that tracks STATUS … that should be part of the PR that accomplished the item." Consumer fixed in PR #41 (`a5553b3`).

## Correction (proposed)

1. Add an explicit status-ownership rule to `skills/triaging-requirements/SKILL.md` (Step 7 / Done-archive rules) and `references/roadmap-format.md`, cross-referencing `reference/git-workflow.md` §Roadmap closure — citation, not copy.
2. Optional, low priority — extend `implementing-features` Step 10's closure bullet to "every status tracker it owns" (roadmap row, plan frontmatter per the repo's stated convention, History entry).

No process behavior change beyond the clarification: triage scores/ranks/horizons the open backlog, reconciles status only when drift is found, and maintains the Done archive (row formatting, verbatim `Success measure`) — it never gates status.
