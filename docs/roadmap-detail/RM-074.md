# RM-074 — Delegation observer signal quality

> Detail file for roadmap row `RM-074`. Status and rank live in
> `docs/ROADMAP.md`; this file is provenance.

Source: owner reports 2026-11-07, during two sessions with background
subagents (RM-073 Phase 1 and the RM-041 closure). RM-072 is the sibling row
for strip coalescing; this row owns scope, classification, terminal aging and
the sidebar's information policy.

## Observed (2026-11-07)

1. **False thrash on healthy work.** One implementer pass editing
   `docs/ROADMAP.md` sequentially (row move, counters, changelog) raised
   `thrash: edit: docs/ROADMAP.md` three times — at `x3`, then `x6`, then
   `x10` — while every edit succeeded and changed the file. The same pattern
   hit `docs/roadmap-detail/RM-041.md` and a reviewer's `grep` on one
   directory.
2. **Completed delegates never age out.** The sidebar listed five
   `completed` delegates with `12h48m`–`14h15m` elapsed and `q12h45m`–`q13h35m`
   quiet, plus `29 stale delegates hidden`. `q` is quiet time
   (`now − lastActivityAt`).
3. **Thrash notices in every session.** The owner saw the notice in sessions
   that did not own the delegate.
4. **Duplicate wake.** The same `thrash:ROADMAP.md` milestone text arrived
   twice for one child.
5. **Unassociated running child.** The banner reported `1 running child
   session(s), 1 with no delegate association`, so the only actionable fact
   was in the banner, not in a row.

## Root causes

- **Terminal aging** — `plugins/delegation-observer/state.ts:363`:
  `if (d.terminal) return d.provenance !== "observed";` A delegate observed
  while running and then completed is never stale; only store-terminal rows
  never observed become history.
- **Scope** — `server.ts:266` bootstraps from an unfiltered
  `ctx.session.list()`; `view.ts:82–84` renders every non-stale delegate;
  `model.ts:212–237` raises `ctx.ui.toast.show` / `ctx.attention.notify` for
  every attention/terminal milestone in that directory-wide state. Only the
  synthetic wake is targeted (`server.ts:220`, `sessionID: parent.rootID`).
  The plugin is activated per location, and the TUI context has no
  active-session binding (`model.test.ts` context mock).
- **Classification** — `state.ts:684–698`: loop key is the tool target, the
  counter increments on every distinct call to it, resets only on a different
  target, and fires at `loopRepeats: 3` (`state.ts:57`). No progress term: it
  does not compare inputs or effects. `scripts/watch_agent.py:296–300` uses
  the opposite policy (edit/write ≥ 8; "re-editing one file is normal
  iteration").
- **Delivery** — `state.ts:588` dedupes milestones per `thrash:<target>` for
  the delegate's lifetime, so the repeated text points at re-delivery or an
  observer-state rebuild. Confirm from the observer log before changing code.

## Acceptance criteria (design-pass inputs, not final until the plan)

1. **Terminal aging and sidebar hygiene.** The sidebar renders
   `running`/`waiting`/`warning` always, `failed` up to 60 min after
   `terminal.at`, and `completed` up to 5 min after `terminal.at`; stale and
   archived rows never. The `N stale delegates hidden` line is removed from
   the sidebar and kept only in `session.panel`. Thresholds are config
   (`terminalGraceSeconds`, env-overridable), with the terminal timestamp
   surfaced in the row projection. *Verify:* fixed-clock reducer/view tests —
   a 12 h observed-completed row is not rendered; a 2 min one is; the sidebar
   is empty when only stale rows exist, with no count line.
2. **Scope attribution.** The bootstrap derives each delegate's root from the
   `parentID` chain; rows are grouped by root (or labelled with the owning
   root) and the toast text names the root. Host-independent: no reliance on
   an active-session API. *Verify:* two roots with children in one directory
   produce rows attributed to their own root; a milestone for root B never
   renders as root A; grouping survives a store-rebuild.
3. **Progress-aware thrash.** The loop key includes the call's input
   fingerprint, or the counter resets when the previous call changed state;
   the edit/write threshold aligns with `watch_agent.py` (8) while bash/read
   stays 3. *Verify:* six distinct edits to one file → zero thrash; three
   identical failing commands → exactly one; the existing re-delivery test
   (`state.test.ts:281–300`) stays green; a break→restore check proves the
   test fails when the progress term is removed.
4. **Wake dedupe.** One wake per (child, condition) survives an observer
   state rebuild; the `maxAttentionWakes` cap still bounds. *Verify:* replay
   the 2026-11-07 event sequence and assert exactly one `session.synthetic`
   call for the target; the existing cap test stays green.

## Open design questions

- Confirm the duplicate-wake cause from the observer log (rebuild vs
  double emission) before choosing the fix.
- Grouping vs filtering: grouping is available today and host-independent;
  filtering to the active root needs a host API that does not exist.
- Whether the sidebar cap stays at 8 or tightens to 5 once terminal aging
  lands.
- Whether RM-072 and RM-074 share one implement pass; they touch the same
  files (`view.ts`, `state.ts`, `tui.tsx`) but have distinct verifiers.

## Scope

`plugins/delegation-observer/{state.ts,view.ts,server.ts,tui.tsx}` and their
tests. RM-070/ADR-0015 wake semantics, the trusted-root gate, the terminal
wake (Python completion observer), and RM-072's coalescing are unchanged.

## Exclusions

- No host/plugin API additions; no changes to `session.list()` itself.
- No re-litigation of the attention-wake contract (RM-070, ADR-0015).
- No changes to `watch_agent.py` beyond keeping the two thresholds aligned.
