## Requirements (AC1–AC18 of the approved plan)

1. `check --pins-only` verifies every active pin seam offline; a stale seam
   fails and names its path.
2. `status`/`check --remote` report pinned/live/latest; the registry check
   drives the weekly issue.
3. `plan --to X` prints the compatibility matrix and breaking-change notes
   before any write.
4. `prepare --dry-run` is read-only; a second real prepare is a no-op.
5. `prepare` updates the adapter/docs/plugin seams, refreshes lockfiles, and
   appends the dated ADR amendment.
6. `canary --to X` installs into scratch, runs C1–C8 + migration with the
   candidate version, and writes evidence; a failed gate stops.
7. The canary typechecks/tests all three plugins against the target
   `@opencode/plugin`/OpenTUI; a source break reports manual migration.
8. `apply` refuses non-TTY, undrained, same-version, or missing-candidate
   states.
9. `apply` verifies binary, `/api/info`, agents, and the plugin loader; any
   failure restores the link + pre-upgrade DB and reports `ROLLED BACK`.
10. `rollback --manifest` restores the link and DB.
11. CI runs `test_opencode_upgrade.py` + `check --pins-only`; the scheduled
    workflow opens/updates one issue per newer version.
12. The 2.2.5 exercise runs `status`/`plan`/`canary` live and the owner
    `apply` verifies the switch.
13. ADR-0016, this row/detail, reference/README/AGENTS, and plan retirement
    land on the branch; the repo gates are green.
14. `status`/`doctor` expose the install topology, last canary/apply, and
    the resumable stage; `upgrade --resume` skips completed stages.
15. `plan` includes release breaking changes and the compatibility matrix.
16. `VERSION_PIN` is the single source: the cutover imports it, CI exports
    it, and `check --pr` enforces the canary amendment.
17. `apply --wait-for-drain`/`--stop-service` smooth the drain; `prepare
    --open-pr` generates the PR body with the gh config env fixed.
18. `prune --keep N` and the lockfile delta summary keep scratch/review
    hygiene.

## What changed

- `scripts/opencode_upgrade.py` — new orchestrator (`status`, `doctor`,
  `check`, `plan`, `prepare`, `canary`, `apply`, `rollback`, `prune`,
  `upgrade`; `--json` on the read paths).
- `scripts/test_opencode_upgrade.py` — 12 hermetic tests covering the seams,
  prepare, plan, status, canary evidence gate, apply consent/auto-rollback,
  drain wait, prune, resume, and the CI single-source derivation.
- `scripts/opencode_v2_canary.py` — `--version` override; C1 installs/asserts
  it and C2 requires the exact version. The canary now stops the C2/C7
  scratch services in a `finally` block; the 2.2.5 test-out exposed a leaked
  C7 service on port 58841, which the live drain gate correctly refused.
- `scripts/opencode_v2_cutover.py` — `VERSION = v2.VERSION_PIN` (no duplicate
  literal); the `--upgrade` mode from PR #140 is the apply vehicle.
- CI: `ci.yml` runs the orchestrator suite + pin gate; the eval workflows
  derive `OPENCODE_VERSION` from the adapter; the new
  `opencode-version-check.yml` is issue-first drift detection.
- Docs: ADR-0016, ADR-0014 pointer, ADR index, reference standard section,
  README upgrade line, AGENTS rule 7, RM-067 pointer.

## 2026-11-02 correction — supported install/upgrade path

The owner challenged the custom versioned wrapper after the live switch:
`opencode upgrade` is the prescribed mechanism, and the versioned layout was
not one of its supported install methods. ADR-0017 supersedes ADR-0016:

- Live install moves to the yarn-global `@opencode/cli` and the default
  `~/.config/opencode` root; `opencode upgrade <target> --method yarn` is the
  live command.
- `scripts/stage_opencode_config.py` migrates the reviewed config with a V1
  backup; the V1 `opencode-ai@1.19.4` package stays shadowed for retention.
- The versioned wrapper, cutover, custom link/DB rollback, and the heavy
  `apply`/`rollback` orchestrator are retired.
- The canary remains the pre-merge gate (C1–C8 + migration + plugin/TUI
  setup smoke); the pin check and weekly drift issue remain.
- The 2.2.5 exercise exposed a sentinel false negative: the observer TUI
  loaded (`features.tui: true`, debug setup complete), but 2.2.5 omits
  `ctx.location.directory` in the TUI, so the presence/health check failed.
  The plugins now fall back to `process.cwd()` and trust a fresh
  health/presence record.

## Live apply (passed 2026-11-02)

The live 2.2.5 switch passed before the supported-path correction:

```sh
opencode service stop
python3 scripts/opencode_upgrade.py apply --to 2.2.5 --drain-acknowledged
opencode --version   # opencode v2.2.5
```

Verified artifact: `.scratch/opencode-v2/upgrade-2.2.5-verify.json`
(binary 2.2.5, `/api/info` 2.2.5, 17 agents, plugin loader). The supported
migration (`stage_opencode_config.py` + `opencode upgrade 2.2.5 --method
yarn`) is the follow-up owner step.
