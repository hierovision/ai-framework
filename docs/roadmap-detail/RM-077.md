# RM-077 — Supported OpenCode upgrade shadow repair and truthful verification

> Detail file for roadmap row `RM-077`. Status and rank live in
> `docs/ROADMAP.md`; this file is provenance.

Source: owner report and live 2026-11-09 `@opencode/cli@2.2.6` install on the
framework host. The release and canary were healthy; the default `opencode`
command was not. Design and approval: plan
`.opencode/plans/rm-077-opencode-upgrade-shadow.md` (approved 2026-11-09;
retired at merge per ADR-0008/AGENTS rule 4). Decision record: ADR-0017
(2026-11-09 amendment).

**Status: done** (2026-11-09). Delivered on branch
`feat/rm-077-opencode-upgrade-shadow`; [PR #170](https://github.com/hierovision/ai-framework/pull/170).

## Defect (observed 2026-11-09)

`@opencode/cli@2.2.6` installed successfully and `opencode2 --version`
returned `opencode v2.2.6`, but `scripts/opencode_upgrade.py upgrade --to
2.2.6 --apply --drain-acknowledged` reported a failed smoke:

```text
verify binary: FAIL 1.19.4
verify api: FAIL
verify plugin: FAIL loader did not load ...
verify observer: FAIL api unavailable
```

An explicit 2.2.6 probe passed (`opencode2 debug paths config`,
`/api/info` version, agent list, plugin loader), so the release was healthy
and the default command was the defect.

## Root cause

Yarn-global retained both `@opencode/cli` and `opencode-ai`; both publish an
`opencode` bin. Yarn linked `opencode2` to V2 but `opencode` to V1, and the
orchestrator assumed its post-install `PATH` lookup still resolved V2. The
failure path also claimed a rollback it did not perform (neither package nor
config/DB was restored), and `status` recommended re-staging a config that was
already supported.

## Requirements (AC1–AC10 of the approved plan)

1. Yarn relink is reproduced hermetically: a V2 `opencode2`, a V1 `opencode`,
   and an official-install stub that rewrites the default link; apply exits 0
   only after repairing to V2 and smoking V2.
2. The repaired binary is the one verified: the smoke receives an explicit
   repaired link and asserts its exact version.
3. Already-installed recovery is idempotent through the CLI: skip the official
   install, repair the shadow, verify, record `applied`.
4. A failed apply is truthful: `verified: false`, `rolled_back: false`, named
   failure stage, target package and default-link evidence, backup path, and
   state at `prepared`.
5. Link repair fails closed: missing/mismatched target binaries or a
   config-root mismatch fail before smoke and never link an unverified
   executable.
6. `status`/`doctor` diagnose the shadow: target package, default version,
   `shadow_ok`, and the exact repair command; no re-staging of a supported
   config.
7. No false rollback claim remains in code, tests, README, reference, or the
   RM-071 detail.
8. The corrective path is documented and executable in README, the reference,
   and the dated ADR-0017 amendment.
9. The current 2.2.6 install is repaired without reinstall (owner-run after
   merge).
10. No canary gate, post-smoke check, pin seam, or assertion is deleted or
    relaxed; the retained V1 package and no custom wrapper remain.

## Review follow-up (2026-11-09)

PR #170 review found three defects, fixed on the same branch:

1. `target_package_info()` no longer fabricates `version=target` when the
   package is absent; it reports the actual `package.json` version or `None`
   (the requested target stays in the artifact's top-level `version`).
   `test_shadow_repair_refuses_missing_or_wrong_target` proves the missing case
   reports `None` and the mismatched case reports `2.2.5`.
2. `last_verify_verified()` normalizes legacy artifacts without `verified`:
   verified only when every check passed and `rolled_back` is false; otherwise
   unverified. `test_upgrade_reverifies_after_legacy_failed_artifact` uses the
   live 2.2.6 shape (`rolled_back: true`, no `verified`) and proves a healthy
   host re-runs the smoke and replaces it with `verified: true`.
3. `status` gates the repair recommendation on `supported_config`; an
   unsupported root now gets migration guidance, not an apply that
   `prepare_shadow()` would refuse.
   `test_status_unsupported_config_uses_migration_guidance` covers it. The
   recorded-target resume branch now names the target
   (`upgrade --to <target> --resume`) and is covered by
   `test_status_names_recorded_target_for_resume`.

No live host/link/config/DB/package mutation was performed.

## Second review follow-up (2026-11-09)

A fresh independent review found one major, one minor, and four nits, fixed on
the same branch:

1. **Truthful rollback semantics.** `apply_supported()` records the complete
   pre-repair default-link state (`previous_default`: path, raw target,
   resolved path, version, V1/V2 kind) before any install/repair. The artifact
   branches: V2 previous uses `opencode upgrade <previous> --method yarn`; V1
   previous restores the original link and the V1 config/DB backup, never
   `opencode upgrade 1.19.4 --method yarn`.
   `test_apply_v1_default_failure_has_v1_rollback` starts from the V1-default
   Yarn-relink scenario and asserts the exact V1 fields, link-restore command,
   guidance, and the absent false upgrade command (plus the V2 branch).
2. **No-apply repair guidance.** `upgrade --to <pin>` without `--apply` now
   detects a repairable shadow before the migrate error and prints the exact
   `--apply --drain-acknowledged` command; migrate guidance is reserved for a
   missing target or genuinely unsupported config.
   `test_upgrade_without_apply_prints_repair_for_v1_default` covers both.
3. **Truthful dry-run text.** `apply --dry-run` says "would install" when no
   target is present and "would repair ... installed" only when it is.
   `test_apply_dry_run_text_truthful` covers both.
4. **Resumable-stage predicate.** `status` suggests `--resume` only for the
   persistent non-terminal stages (`checked`, `planned`, `canaried`,
   `prepared`) and never for legacy `rolled-back`; the command always names the
   recorded target. The resume test covers both.
5. **Forced state regression.** `write_state(..., force=True)` on a failed
   re-apply moves `applied` back to `prepared`;
   `test_failed_reapply_regresses_applied_to_prepared` proves the intended
   transition.
6. **Neutral artifact builder.** `failure_payload` is renamed to
   `apply_artifact` and builds both success and failure evidence; fields and
   tests stay coherent.

No live host/link/config/DB/package mutation was performed.

## Third review follow-up (2026-11-09)

A fresh independent review found two must-change findings and two nits, fixed
on the same branch:

- **M1 — preserve the pre-existing failed artifact.**
  `write_apply_artifact()` archives an existing non-verified
  `upgrade-<target>-verify.json` to
  `upgrade-<target>-verify.json.failed-<UTC stamp>` (exact bytes,
  `os.replace`) before writing new evidence. A verified predecessor is never
  mislabeled; `archive_failed_artifact()` returns `None` for it.
  `test_upgrade_reverifies_after_legacy_failed_artifact` starts from the live
  legacy failure shape and asserts the archive is byte-identical, the new
  artifact is verified, and a verified predecessor is not archived.
- **m1 — truthful unknown/missing rollback.** `rollback_plan()` has an explicit
  `unknown` branch for a missing/unclassifiable `previous_default`; it emits
  no command and its guidance makes no V1/V2 claim.
  `test_rollback_plan_unknown_previous` covers it. V1 and V2 keep their own
  branches.
- **n1 — label repair vs verification.** `upgrade --to <pin>` without
  `--apply` prints `verification needed:` when the shadow is healthy but the
  last artifact is stale/unverified, and `shadow repair needed:` only for a
  broken shadow. `test_upgrade_without_apply_prints_repair_for_v1_default`
  covers both labels.
- **n2 — version-generic README command.** The recovery command is now
  `upgrade --to <pin> --apply --drain-acknowledged` (no hardcoded `2.2.6`);
  `test_upgrade_docs_describe_supported_shadow` asserts the generic command
  and rejects `upgrade --to 2.2.6`.

No live host/link/config/DB/package mutation was performed.

## Exhaustive hardening (2026-11-09 owner directive)

The first end-to-end exercise failed, so every upgrade-path finding — including
pre-existing defects and nits — was fixed with a regression test:

- **B1 (blocker) false generated rollback text.** `append_adr_amendment`
  writes the real `upgrade --to <pin> --apply --drain-acknowledged` command and
  "no automatic rollback"; ADR-0014's checked-in amendment is corrected.
  `test_upgrade_docs_describe_supported_shadow` rejects "rolls back link + DB"
  and the nonexistent `opencode_upgrade.py apply`.
- **M1 V1 rollback pointer.** `rollback_plan` locates the actual
  `~/.config/opencode.v1-backup-*` tree/DB, distinguishes the V2-era pre-apply
  snapshot, and states the first-install/no-backup case truthfully.
  `test_apply_v1_default_failure_has_v1_rollback` and
  `test_rollback_plan_v1_without_backup_is_truthful` assert exact guidance.
- **M2a dry-run purity.** `--dry-run --stop-service` does no stop, backup,
  install, link repair, or state write. `test_apply_dry_run_is_side_effect_free`.
- **M2b stop ordering.** An explicit stop runs before the drain re-check.
  `test_apply_stops_service_before_drain_gate`.
- **M3 backup permissions.** One shared `opencode_v2.sqlite_backup` writes every
  DB copy 0600; upgrade/stage/canary delegate to it.
  `test_sqlite_backups_are_0600`, the stage backup mode assertion, and the
  canary migration rehearsal mode assertion. Owner post-merge action:
  `chmod 600 ~/.config/opencode.v1-backup-*/opencode.db
  ~/.scratch/opencode-v2/pre-upgrade-*/opencode.db 2>/dev/null`.
- **M4 exception-safe apply.** Timeouts/spawn errors during stop, backup,
  install, shadow, or smoke produce a named `exception:<stage>` artifact and
  `prepared` state. `test_apply_timeout_writes_failure_artifact`,
  `test_apply_spawn_error_writes_failure_artifact`.
- **m1 canary prerequisite/residual.** Missing/failing evidence names the
  evidence root and `--skip-canary`; a non-zero migration residual is accepted
  only with a dated classification record. `test_canary_residual_acceptance`,
  `test_apply_missing_canary_message_surfaces_skip`.
- **m2 DB path precedence.** `--home` and `OPENCODE_DB` drive the backup source;
  an absent first-install DB yields no fabricated backup path.
  `test_pre_upgrade_backup_uses_home_and_absent_db`.
- **m3 live agents.** The smoke verifies expected framework IDs in the live
  `/api/agent` response and tolerates built-ins/new agents.
  `test_check_agents_live_tolerates_extras_and_flags_missing`.
- **m4 exact versions.** Binary/API/canary checks parse and compare the exact
  version. `test_version_parsing_rejects_substrings`,
  `test_check_version_is_exact`, `test_exact_version_helpers`.
- **m5 prepare ordering.** The canary gate runs before any seam/package write or
  npm install; `--allow-pending-canary` is the explicit bypass.
  `test_prepare_gate_precedes_writes`,
  `test_prepare_allow_pending_canary_is_explicit_bypass`.
- **m6 predecessor preservation.** Every predecessor is archived before
  overwrite: `.failed-<stamp>` unverified, `.previous-<stamp>` verified.
  `test_upgrade_reverifies_after_legacy_failed_artifact`.
- **m7 `check --pr` claim.** Documented as a local/manual release gate; CI runs
  only `check --pins-only` and the hermetic suite. Docs assertion in
  `test_upgrade_docs_describe_supported_shadow`.
- **m8 PATH/link divergence.** Topology/status/doctor and the official upgrade
  use the explicit link, not `PATH`. `test_topology_uses_explicit_link_not_path`.
- **m9 canary tautology/C7.** Migration membership is a real partition check;
  C7 asserts the marker agent, plugin row, and live agent. New canary tests.
- **n1 docstring/CLI truth.** No nonexistent `apply`/`rollback` subcommands or

- **n2 pin-generic docs assertion.** `test_upgrade_docs_describe_supported_shadow`

- **n3 `--backup` no-op.** Documented in help/docstring; tested by
  `test_backup_flag_is_documented_noop`.
- **n4 dead code.** Removed dead constants, the broken post-smoke `run` return,
  the unused stage import, and consolidated the triplicated backup helper.
  `test_run_spawn_error_returns_completed_process`.
- **n5 range logic.** Caret/tilde/x/compound ranges are evaluated honestly

- **n6 unused stage.** `checked` is removed from the state contract

- **n8 atomic/locked writes.** JSON is temp+`os.replace`; state/artifact writes

## Owner repair after merge

The 2.2.6 host repair is owner-run from a normal terminal with all sessions
closed; it reuses the installed package (no Yarn), repairs the shadow, and
writes passing evidence:

```sh
python3 scripts/opencode_upgrade.py upgrade --to 2.2.6 --apply \
  --drain-acknowledged --stop-service
python3 scripts/opencode_upgrade.py status
python3 scripts/opencode_upgrade.py doctor
```

The pre-existing failed `upgrade-2.2.6-verify.json` is automatically archived
byte-identically as `upgrade-2.2.6-verify.json.failed-<UTC stamp>` (an
unverified predecessor; a verified one would use `.previous-<UTC stamp>`)
before the new evidence is written. Existing DB backups created before the 0600
fix get the one-time owner chmod:
`chmod 600 ~/.config/opencode.v1-backup-*/opencode.db
~/.scratch/opencode-v2/pre-upgrade-*/opencode.db 2>/dev/null`.

Expected: `opencode --version` and `opencode2 --version` both print
`opencode v2.2.6`, `opencode debug paths config` is
`~/.config/opencode`, `upgrade-2.2.6-verify.json` has `verified: true`, and
`upgrade-state.json` is `applied`.
